# CPU 实测记录：贪心投机解码

日期：2026-11-03（北京时间）。代码基于 `cf811bef6454dd7a9959b5854af13a52d7ba79f5`。
补丁源码指纹见文末；实现当时尚未提交，因此 base revision 不是实现版本。

环境：AMD EPYC 9V74 虚拟化 x86_64 CPU，Python 3.12.14，PyTorch 2.15.0+cpu，float32，单线程，无 GPU。
3 组基准逐组运行，没有与仓库测试并发执行。主机频率与调度不受控，时延不是硬件性能保证。

共同配置：seed=42，输出 32 token，每个上下文长度 3 个 prompt，每个组合预热 2 次，
每个 prompt 重复计时 5 次，因此每行各有 15 个 baseline/speculative 样本。
时延列为全部样本的中位数 [最小值, 最大值]；speedup 为两个中位数的比。
接受统计按 3 个不同 prompt 合并，不因重复计时把相同输出重复计数。
所有 36 组配置、108 个 prompt/K 条件及 540 次计时投机请求均与目标模型贪心结果完全一致，
对应普通 KV 解码也逐次比对；每种目标/prompt 的 naive 完整重算另行检查。

这些 prompt 来自与训练相同的简单循环分布。100% 接受率不是语言任务结果；
长度 96 也不是 K3 长上下文验证。

## 可作出的结论

- 此 CPU 设置下，训练 plain 草稿 K=8 的三种上下文观测到 1.138–1.240×；K=1/2 更慢，K=4 接近或略慢于普通解码。
- Engram 草稿同样达到该合成任务的 100% 接受率，但 0.422–0.689×，比普通 KV 解码更慢；没有观察到 Engram 接受优势。
- 随机模型在此 seed/任务下所有草稿均被拒绝（0%），倍率 0.146–0.321×，负面结果符合额外草拟和验证开销。
- K=4 的 3.714 个接受草稿/轮与 4.571 个输出/轮是不同口径；K=8 的 7.250 和 8.000 同样受 32-token 输出尾块影响。
- 高接受率本身不能证明端到端加速；这些有限样本不能说明最佳 K 的普适值，或 Kimi K3 的任何收益。
